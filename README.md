# 플러그인게시판 (plugin_board)

BookOasis 좌측 사이드바에 전용 카테고리 탭을 추가해, BookOasis 플러그인 저장소 목록을
색인 카드 형태로 보여주는 플러그인입니다. 카드에서 바로 **신규설치 / 업데이트 /
활성화·비활성화 / 환경설정 / 삭제**까지 수행할 수 있으며, 외부 플러그인(plugin_manager
등) 없이 **완전히 독립적으로** 동작합니다.

## 버전 및 호환 정보

| 항목      | 값                                            |
| ------- | --------------------------------------------- |
| 플러그인 버전 | `2.40.0`                                      |
| 플러그인 ID | `plugin_board`                                |
| 표시 이름   | 플러그인게시판                                       |
| 클래스     | `PluginBoardMetadataProvider`                 |
| 모듈      | `plugins.metadata.plugin_board.plugin_board`  |
| 유형      | 카테고리 풀페이지 탭 + 자체 설치/업데이트/관리 엔진 내장           |
| 외부 의존성  | 없음 (plugin_manager 불필요)                       |

**v2.40.0**: 별도로 관리하던 큐레이션 목록 파일(`plugin_list.txt`)을 완전히
제거했습니다. GitHub Topics 검색(§2-1)이 이미 카드 목록 수집을 대신하고 있어서
더 이상 필요하지 않다는 판단입니다. `plugin_board` 자기 자신은 여전히
`SELF_REPO_URL`로 별도 조회해 항상 맨 앞에 표시되고, `github.txt` 레지스트리
(§2-2)와 로컬 설치 스캔(§4)도 그대로 유지됩니다 — 목록 파일 하나만 빠졌을 뿐,
나머지 발견/추적 경로는 전과 동일합니다.

이 플러그인은 BookOasis의 권장 폴더형 플러그인 구조를 사용하며, 전역 테마 CSS 변수
(`var(--app-*)`)로 스타일을 구성해 8종 대시보드 테마와 자동으로 동기화됩니다. 버튼·배지·
태그는 테마 강조색을 진하게 채우는 대신 `color-mix()`로 옅게 섞은 톤(테두리+반투명 배경)을
써서 테마가 밝은 강조색(예: 청록/네온 계열)이어도 카드 전체가 튀지 않고 차분하게 보이도록
했습니다.

## 동작 방식

### 1. 카드로 보여줄 저장소 목록 자체를 GitHub Topics 검색으로 실시간 조회

카드로 보여줄 GitHub 저장소 **목록 자체**를 코드에 하드코딩하거나 별도 목록
파일로 관리하지 않습니다. 대신 GitHub **Topics**(`bookoasis-plugin`)에 이
토픽이 달린 공개 저장소를 화면을 열 때마다(`get_dashboard_data` 호출 시)
Search API로 실시간 검색합니다(자세한 동작은 §2-1 참고).

저장소 소유자가 자기 GitHub 저장소 설정에서 이 토픽만 추가하면, 별도 목록
파일을 고칠 필요 없이 다음 로드부터 자동으로 카드에 나타납니다. 검증 없이
자동 노출되므로 카드에는 "⚠ 미검수 · 토픽 발견" 표시가 붙습니다.

토픽 검색 결과에 아직 안 잡힌 저장소(토픽을 안 달았거나, 이제 막 만든 경우
등)는 Git 저장소 URL 설치 패널(§6)로 직접 설치하면, 이후 §2-2의 `github.txt`
레지스트리로 계속 추적됩니다.

캐시 만료(최대 1시간)를 기다리지 않고 즉시 반영하고 싶다면, 화면 우측 상단의
**`목록 새로고침`** 버튼을 누르면 됩니다. GitHub Topics 검색 결과, **그리고
설명·최신 버전 캐시(`_DESC_CACHE`/`_VERSION_CACHE`)까지 모두 강제로 다시
조회**합니다(v2.34.1부터 — 이전 버전은 토픽 캐시만 비우고 버전 캐시는 그대로
둬서, 버튼을 눌러도 "설치된 버전 vs 최신 버전" 비교 결과가 최대 1시간 동안
옛날 값으로 남아있는 문제가 있었습니다). 설치 여부·설치된 버전·활성화 여부는
항상 서버 파일시스템에서 즉시 읽어오므로(§3) 이 버튼과 무관하게 이미 최신
상태이며, 이 버튼이 갱신하는 건 "GitHub/Gitea에 최신 버전이 있는지" 쪽입니다.

**`plugin_board` 자기 자신은 토픽 검색 결과와 무관하게 항상 카드로 표시되며,
항상 맨 앞에 정렬됩니다.** `get_dashboard_data()`가 `SELF_REPO_URL`
(`https://github.com/yume-script/plugin_board`)을 별도로 직접 조회해서
카드 목록 맨 앞에 고정합니다("미검수" 표시 없이). 그 결과 자기 자신도 다른
카드와 완전히 동일하게 설명·최신 버전·업데이트 확인·`업데이트` 버튼을 그대로
씁니다 — 코어의 별도 자동 업데이트 화면(환경설정 > 플러그인 설정의 샘플 업데이트
버튼)에 기대지 않고, 이 화면 안에서 스스로를 관리할 수 있습니다. 삭제·비활성화는
`_delete_plugin`/`_toggle_plugin_enabled`가 여전히 거부하며, 프론트엔드에서도 자기
카드에는 그 두 컨트롤(스위치·삭제 버튼)만 표시하지 않습니다(눌러도 거부될 걸 미리 숨김).
**단, `GitHub Personal Access Token` 같은 설정 항목은 정상적으로 편집 가능하므로,
환경설정(⚙) 버튼은 삭제/비활성화와 달리 자기 카드에도 그대로 표시됩니다** — 초기 버전에서는
관리 행 전체를 통째로 숨겨서 설정 버튼까지 함께 사라졌던 버그가 있었고, v2.22.2에서
수정되었습니다.

### 2. 카드 정보 — 저장소별로 GitHub에서 실시간 조회

카드 내용(제목·설명·최신 버전)도 코드에 직접 적어두지 않고, 저장소별로 실시간 조회합니다.

| 가져오는 값 | 조회 위치 | 캐시 TTL | 비고 |
| --- | --- | --- | --- |
| 목록 자체 | GitHub Topics 검색(`api.github.com/search/repositories`) | 1시간 | §2-1 참고 |
| 설명, 토픽(태그) | GitHub 저장소 API (`api.github.com`) | **24시간** | 시간당 60회 무인증 한도 |
| 최신 버전 | 저장소의 `VERSION` 파일 (`raw.githubusercontent.com`) | **1시간** | 인증 없이 무제한 |

카드에 표시되는 GitHub Topics 태그는 `#bookoasis-plugin`처럼 **해시태그 표기**로
보여줍니다(`madnite1/plugin_manager`의 카드 표기를 참고) — 저희가 자체 분류한
"검색형 메타데이터"/"카테고리 탭 UI" 같은 태그와 시각적으로 구분하기 위함입니다.

카드 헤더 좌측에는 분류(검색형/카테고리 탭/기타)에 따라 색이 다른 아이콘 배지가
붙습니다. 아이콘을 새로 그리지 않고 [Lucide Icons](https://lucide.dev)(ISC 라이선스,
자유 재사용 가능)의 `search`/`layout-grid`/`puzzle` 아이콘 path를 그대로 가져와
씁니다 — 검색형은 돋보기, 카테고리 탭은 그리드, 기타는 퍼즐 조각 아이콘입니다.

**설명/토픽과 버전은 캐시 수명이 다르게 분리되어 있습니다.** 설명·토픽은 저장소
관리자가 잘 바꾸지 않는 값이라 24시간 캐시하고, 버전은 릴리즈 주기를 반영해 1시간마다
새로 확인합니다. 버전 캐시만 만료된 경우 설명 캐시가 아직 살아있으면 `api.github.com`을
다시 호출하지 않고 `VERSION` 파일만 조회합니다 — 캐시 만료 주기마다 매번 두 요청을 다
보내던 것보다 시간당 평균 API 호출 수가 줄어듭니다.

API 조회가 실패해도(예: rate limit) `VERSION` 파일만은 `main`/`master` 브랜치로
재시도해 최대한 버전 정보를 채우고, 카드에는 붉은 테두리로 조회 실패 사실을 표시합니다.

**저장소별 조회는 순차가 아니라 병렬로 처리됩니다** (`ThreadPoolExecutor`, 최대 동시
8개). 캐시가 만료된 콜드 로딩 기준, 저장소가 N개면 순차 방식은 대기 시간이 N배로
늘어나지만 병렬 방식은 "가장 느린 요청 1개" 수준으로 수렴합니다. 실측 기준 저장소
9개에서 순차 대비 약 3배 이상 빨랐습니다. 캐시가 살아있는 저장소는 스레드 안에서도
즉시 반환되므로 병렬화 자체의 추가 비용은 없습니다.

### 2-1. GitHub Topics 검색 — 카드 목록의 유일한 수집 경로

GitHub **Topics**에 `bookoasis-plugin` 토픽이 달린 저장소를
[Search API](https://docs.github.com/en/rest/search/search)
(`/search/repositories?q=topic:...`)로 찾아 카드로 보여줍니다. 저장소
소유자가 자기 GitHub 저장소 설정에서 이 토픽만 추가하면, 다음 로드부터
자동으로 카드가 뜹니다.

- **토픽 목록**: 코드의 `DISCOVERY_TOPICS = ["bookoasis-plugin"]`이 기본값입니다.
  플러그인 설정 화면의 `추가 발견 토픽(EXTRA_DISCOVERY_TOPICS)`에 콤마로 구분해
  입력하면 코드 배포 없이 검색 대상 토픽을 늘릴 수 있습니다.
- **노이즈 필터**: 토픽은 GitHub 전역에서 공유되는 이름이라, 흔한 단어를 추가
  토픽으로 넣으면 전혀 무관한 저장소가 대량으로 섞여 들어올 수 있습니다(실측:
  흔한 이름 하나로 무관한 저장소 50개 이상이 잡힌 사례가 있었습니다). 그래서
  **`VERSION` 파일을 실제로 찾은 저장소만** 카드로 인정합니다(이미 설치된
  저장소는 예외적으로 항상 허용). 그래도 남는 개수는 30개로 한 번 더 자릅니다.
- **미검수 표시**: 검색으로 찾은 카드는 신규설치/업데이트가 가능하지만,
  `⚠ 미검수 · 토픽 발견` 태그가 항상 붙어 "관리자가 직접 확인하고 올린 목록이
  아니다"라는 걸 명확히 구분합니다(§2-2·§4의 다른 경로로 추적되는 카드와 달리
  이 태그는 검증 없이 자동 노출됐다는 뜻입니다).
- **캐시**: 검색 결과는 1시간 캐시합니다. GitHub Search API는 일반 API보다 훨씬
  빡빡한 요청 제한(무인증 10회/분, 인증 30회/분)이 있지만, 1시간에 한 번만
  호출하므로 실질적으로 문제되지 않습니다. 헤더의 `목록 새로고침` 버튼을 누르면
  이 캐시도 함께 강제로 비워지므로, 새로 토픽을 단 저장소를 1시간 기다리지 않고
  바로 확인할 수 있습니다.
- **plugin_board 자기 자신은 예외**: §1에서 설명한 대로 `SELF_REPO_URL`로 항상
  별도 조회되므로, 토픽을 달았더라도 검색 결과에서는 제외해 중복 카드가 뜨지
  않도록 합니다.

### 2-2. 직접 설치 이력(github.txt) — 토픽 검색 없이도 계속 추적

GitHub Topics(커뮤니티 자율 태그)는 이 플러그인이 통제할 수 없는 **외부
신호**입니다 — 저장소 소유자가 토픽을 지우면 그 카드는 다시 §4의 밋밋한
"미등록 설치 플러그인"(GitHub 정보 없음) 카드로 강등됩니다. 이를 막기 위해,
**Git 저장소 URL로 직접 설치(또는 업데이트)에 성공한 저장소 주소는 이
서버에 독자적으로 기록**해둡니다.

- **기록 위치**: `plugins/data/plugin_board/github.txt` (한 줄에 저장소 주소 하나,
  `plugins/metadata/plugin_board/`와는 별개의 위치입니다 — 코드가 아니라 이
  서버만의 설치 이력 데이터이므로, plugin_board 자기 자신을 업데이트해도
  건드리지 않고 배포 zip에도 포함되지 않습니다).
- **기록 시점**: 카드의 `신규설치`/`업데이트` 버튼이든 상단 Git 저장소 URL 설치
  패널이든, `_install_or_update`가 성공할 때마다 자동으로 기록됩니다(이미 같은
  저장소 이름이 등록돼 있으면 중복 추가하지 않음). 별도 설정 없이 항상 동작합니다.
  기록 자체가 실패해도(디스크 쓰기 실패 등) 설치 성공 여부에는 영향을 주지 않습니다.
- **표시**: 토픽으로 발견되지 않았지만 이 레지스트리에 있는 저장소는 다른 카드와
  동일하게 설명·최신 버전·업데이트 확인이 되는 카드로 표시되며, `직접 설치됨`
  태그가 붙어 출처를 구분합니다.
- **우선순위**: `plugin_board` 자기 자신 > GitHub Topics 발견 > github.txt
  레지스트리 > 파일시스템만으로 확인한 미등록 카드(§4) 순으로 병합되며, 상위
  출처에 이미 있는 저장소는 레지스트리 카드로 중복 표시되지 않습니다.

### 2-3. 비공개(private) 저장소 설치 — GITHUB_TOKEN 또는 URL 내장 토큰

GitHub는 더 이상 아이디+비밀번호 방식 인증을 지원하지 않습니다(2021년 폐지). 대신
**Personal Access Token(PAT)**이 필요하며, 두 가지 방법으로 쓸 수 있습니다.

1. **설정의 `GITHUB_TOKEN`** — 공개 저장소 API 한도를 늘리는 용도로도 함께 쓰이는
   범용 설정입니다. 이 토큰이 읽기 권한을 가진 비공개 저장소라면 별도 조치 없이
   그대로 설치·업데이트·추적됩니다.
2. **URL에 직접 담기** — `https://아이디:토큰@github.com/owner/repo` 형식으로 Git
   저장소 URL 설치 패널에 붙여넣으면, 그 저장소만 이 토큰으로 인증합니다(§2-4에서
   Gitea와 동일한 방식으로 자세히 설명). 서로 다른 계정의 비공개 저장소를 여러 개
   섞어 쓸 때 유용합니다 — 저장소마다 다른 토큰을 URL에 담으면 되므로, 전역 설정
   하나로는 안 되는 "저장소별로 다른 자격증명"을 지원합니다.

- **공개 저장소용 토큰과의 차이**: §헤더의 "GitHub 토큰 발급 안내" 패널에서 안내하는
  토큰은 *아무 권한도 없는(Repository access: None)* 토큰이라 공개 저장소 API
  한도만 늘려줍니다. 비공개 저장소를 설치하려면 **그 저장소에 대한 읽기 권한이
  실제로 있는 토큰**이 필요합니다 — Fine-grained PAT라면 `Repository access`에서
  해당 저장소를 선택하고 `Contents: Read-only` 권한을 부여하세요.
- **내부 동작**: `api.github.com`, `raw.githubusercontent.com`(VERSION 파일),
  `codeload.github.com`(zip 다운로드) 세 곳 모두에 같은 `GITHUB_TOKEN`을
  `Authorization: token <PAT>` 헤더로 실어 보냅니다. `api.github.com`은
  `Authorization: Bearer`도 인식하지만, `raw.githubusercontent.com`과
  `codeload.github.com`은 `token` 표기만 확실히 동작해서 세 서비스 모두에서
  통하는 `token` 표기로 통일했습니다(v2.30.0에서 수정 — 이전 버전은 `Bearer`만
  써서 비공개 저장소의 VERSION 조회·zip 다운로드가 실패했을 수 있습니다).
- **한계**: `codeload.github.com`의 zip 다운로드는 `/zip/refs/heads/{branch}`
  형식을 사용합니다. GitHub 커뮤니티에서 확인된 예시는 `/legacy.zip/{branch}`
  형식 기준이라, 조직(organization) 소유의 비공개 저장소나 SSO가 강제된
  조직에서는 추가 설정(토큰에 조직 SSO 인가 등)이 필요할 수 있습니다. 문제가
  있으면 GitHub 조직 설정에서 토큰에 대한 SSO 인가 여부를 확인해주세요.

### 2-4. 자체 호스팅 Gitea/Forgejo 서버 지원 — URL 자체가 곧 인증 정보 (v2.32.0)

GitHub뿐 아니라, **GitHub가 아닌 모든 호스트의 저장소를 Gitea 호환 REST API로
자동 처리합니다.** `github.com`이 아닌 호스트는 서버별 허용 목록 없이 전부
시도하며, 인증이 필요하면 **URL 자체에 자격증명을 담아서** 씁니다:

```
https://아이디:비밀번호@gitea.example.com/owner/repo
```

**v2.32.1**: 위 방식으로 백엔드는 이미 지원하고 있었는데, "Git 저장소 URL 설치"
패널의 **프론트엔드 입력 검증이 여전히 `github.com` 호스트만 허용하는 옛 정규식**을
쓰고 있어서, Gitea 주소를 입력하면 백엔드까지 가지도 못하고 "올바른 GitHub 저장소
주소를 입력해주세요" 오류로 막혔습니다. 호스트를 가리지 않는 정규식으로 고쳤고,
입력창 placeholder도 두 형식을 모두 예시로 보여주도록 갱신했습니다.

**v2.32.2**: 카드의 `업데이트` 버튼과 자동 업데이트(§9)가 **화면 표시용
URL(`item.url`, 자격증명이 빠진 상태)을 그대로 `git_url`로 보내고 있어서, 백엔드가
`github.txt`에 저장해둔 자격증명 포함 URL을 찾는 폴백(§2-2, `git_url`이 비어있을
때만 동작)이 아예 발동하지 않는 문제**가 있었습니다. 인증이 필요한 저장소는 최초
설치는 되어도 이후 업데이트는 실패했을 것입니다. 업데이트 요청에서는 `git_url`
자체를 보내지 않도록 고쳐서, 백엔드가 항상 `plugin_id` 기준으로 `github.txt`의
저장된 URL(자격증명 포함)을 직접 찾아 쓰도록 했습니다 — 실제로 자격증명이 담긴
URL로 설치한 뒤 `plugin_id`만으로 업데이트를 재현해, 저장된 아이디/비밀번호가
정확히 재사용되는 것까지 확인했습니다. (신규설치는 사용자가 방금 입력한 URL을
그대로 써야 하므로 이 변경의 영향을 받지 않습니다.)

**왜 서버 설정(`GITEA_HOST` 등) 방식을 쓰지 않았나** — 초기 버전(v2.31.0)은
`GITEA_HOST`/`GITEA_USERNAME`/`GITEA_PASSWORD`/`GITEA_TOKEN` 설정 필드로 Gitea
서버 하나를 지정하는 방식이었습니다. 하지만 이러면 **Gitea 서버를 하나만 쓸 수
있고, 새로운 도메인이나 다른 계정을 추가로 쓰려면 설정을 계속 바꿔야 하는
근본적인 한계**가 있었습니다. v2.32.0부터는 이 설정 필드들을 전부 없애고, 저장소
주소(URL) 자체에 자격증명을 담아 쓰는 방식으로 바꿨습니다 — 저장소마다 완전히
다른 Gitea 서버·다른 계정을 자유롭게 섞어 써도 서로 전혀 간섭하지 않습니다.
**GitHub도 동일한 방식을 씁니다**: `https://아이디:토큰@github.com/owner/repo`
형식으로 저장소별로 다른 자격증명(예: 다른 계정의 비공개 저장소)을 줄 수 있습니다.

**동작 방식**

1. URL에 `아이디:비밀번호@`(또는 `토큰@`, 아이디 자리만 채운 경우)가 있으면
   `_extract_url_credentials()`가 분리해냅니다.
2. **설치에 성공하면 자격증명이 담긴 URL을 그대로(정제하지 않고) `github.txt`
   레지스트리에 기록**해, 다음에 대시보드를 열어 업데이트를 확인할 때도 같은
   자격증명을 그대로 재사용합니다. 별도 서버 설정이 전혀 필요 없습니다. 이미
   등록된 저장소를 자격증명이 담긴 URL로 다시 설치하면, 그 최신 URL로 갱신되어
   계속 인증이 유지됩니다.
   - ⚠️ **이 파일에는 비밀번호가 평문으로 저장됩니다.** 개인적으로 운영하는
     서버라 문제가 없다는 전제로 선택한 방식입니다 — 여러 사람이 접근하는
     서버라면 이 파일(`plugins/data/plugin_board/github.txt`)의 파일 권한을
     직접 제한해두는 걸 권장합니다.
3. GitHub 저장소는 URL의 `비밀번호` 자리(없으면 `아이디` 자리)를 API 토큰으로
   사용합니다. 자격증명이 없는 URL은 여전히 설정의 `GITHUB_TOKEN`(공개 저장소
   API 한도를 늘리는 범용 토큰)으로 폴백합니다 — 이 설정은 "특정 저장소 하나"가
   아니라 "공개 저장소 전체"에 적용되는 서로 다른 성격이라 그대로 남겨뒀습니다.
4. Gitea(비 GitHub) 저장소는 URL의 `아이디`+`비밀번호`를 그대로 Basic Auth로,
   `아이디` 자리만 있으면(비밀번호 없이) 액세스 토큰(`Authorization: token`)으로
   간주해 사용합니다.

**내부적으로 쓰는 Gitea API 엔드포인트** (전부 공식 문서/커뮤니티 사례로 확인한 형식)

- 저장소 정보(설명·기본 브랜치): `GET /api/v1/repos/{owner}/{repo}`
- 버전 파일(`VERSION`): `GET /api/v1/repos/{owner}/{repo}/raw/{branch}/VERSION` — 브랜치를
  쿼리 파라미터(`?ref=`)가 아니라 **경로에 직접 포함**하는 형식을 씁니다. Gitea
  1.23부터 `?ref=` 방식이 제거되었기 때문에, 구버전·신버전 모두에서 동작하는
  경로 방식으로 통일했습니다.
- 소스 다운로드: `GET /api/v1/repos/{owner}/{repo}/archive/{branch}.zip`

**GitHub와의 차이점(현재 지원 범위)**

- **GitHub Topics 방식의 자동 발견(§2-1)은 Gitea에는 적용되지 않습니다.** Gitea
  저장소는 Git 저장소 URL 설치 패널로 직접 설치하는 방식으로만 등록할 수
  있습니다. 한 번 설치하면 §2-2의 `github.txt` 레지스트리에 기록되어 이후에도
  계속 추적됩니다(GitHub 저장소와 동일하게 동작 — 이 파일은 호스트를 가리지
  않고 저장소 주소를 그대로 저장합니다).
- 카드에 표시되는 태그(토픽)는 Gitea 저장소에 대해서는 비어 있습니다(v1 미지원).
- GitHub 저장소용 캐시(`_DESC_CACHE`/`_VERSION_CACHE`)와 키를 분리(`gitea:호스트/...`
  접두어)해서 같은 저장소 이름이라도 서로 캐시가 섞이지 않습니다.
- 카드 하단 링크는 GitHub 저장소면 `GitHub` 버튼, Gitea 저장소면 `Gitea` 버튼으로
  자동 구분됩니다.

**실제 검증한 시나리오** — 완전히 다른 두 Gitea 서버(도메인 자체가 다름)를 각각
다른 계정으로, 설정에 아무것도 등록하지 않고 동시에 설치·추적하는 것까지
테스트해 정상 동작을 확인했습니다. GitHub 저장소 설치/업데이트 회귀 테스트도
함께 통과했습니다.

### 3. 설치 여부 — 서버 파일시스템을 직접 확인

`plugin_board.py`는 자기 자신도 `plugins/metadata/plugin_board/`에 위치한다는 점을
이용해, **부모 디렉토리(`plugins/metadata/`)를 직접 조회**해서 각 카드가 이 서버에
이미 설치되어 있는지, 설치돼 있다면 어떤 버전인지 판단합니다. 외부 플러그인 조회 없이
파일시스템만 보므로 plugin_manager가 없어도 정상 동작합니다.

- 설치 여부: `plugins/metadata/{repo}/` 폴더 존재 여부
- 설치된 버전: 그 폴더의 `VERSION` 파일
- 업데이트 필요 여부: 설치된 버전과 GitHub의 최신 버전을 비교(`x.y.z` 형식 기준)
- **표시 제목**: 설치돼 있으면 저장소 이름(`id`) 대신 실제 클래스의 `name` 속성을
  AST로 읽어 카드 제목으로 씁니다(예: 저장소 `kyobobook` → 카드 제목 "교보문고
  (KyoboBook)"). 아직 설치되지 않은 카드는 `name`을 알 수 없으므로 저장소 이름을
  그대로 씁니다.

### 4. GitHub Topics로 발견되지 않지만 서버에 설치된 플러그인도 같은 그리드에 표시

`plugins/metadata/` 디렉토리를 스캔해서, 토픽 검색·레지스트리 어느 쪽으로도
추적되지 않지만 이미 설치되어 있는 모든 메타데이터 플러그인을 찾아 **같은 카드
그리드에 함께** 보여줍니다(별도 섹션 없음). GitHub 저장소 주소를 모르므로 이
카드들은:

- 설치된 `{plugin_id}.py`에서 `name`/`is_searchable`/`category_tab`/`config_schema`를
  AST로만 읽어 표시 이름·분류·설정 보유 여부를 최대한 정확히 추정합니다.
- GitHub 설명·최신 버전·업데이트 확인은 제공하지 않으며, 카드에 **`로컬플러그인`**
  태그가 붙어 GitHub 정보 없이 서버에 설치된 파일만으로 확인한 카드임을 표시합니다.
- 이미 설치되어 있으므로 설치/업데이트 버튼 없이 관리 행(활성화 스위치·환경설정·삭제)만
  표시됩니다.
- `plugin_board` 자기 자신은 이 스캔에서 제외됩니다.

이 저장소에 나중에 `bookoasis-plugin` 토픽을 달거나(§2-1) Git URL로 다시 설치하면
(§2-2), 다음 로드부터는 설명·최신 버전·업데이트 확인이 모두 활성화된 카드로
승격됩니다.

### 5. 신규설치 / 업데이트 — 전체 재다운로드 방식 (git 불필요)

각 카드 버튼은 상태에 따라 자동으로 바뀝니다.

| 상태 | 버튼 | 상단 버전 스탬프 |
| --- | --- | --- |
| 설치 안 됨 | `신규설치` | 표시 (설치 가능한 최신 버전) |
| 설치됨 + 업데이트 있음 | `업데이트` (+ "업데이트 가능" 태그) | 표시 (업데이트 대상 버전) |
| 설치됨 + 최신 버전 | 초록색 `설치됨` 배지 (버튼 없음) | **생략** — 배지에 이미 버전이 포함되어 있어 중복 표시하지 않음 |

버튼 클릭 시 다음 순서로 서버에서 처리합니다. `update_manifest.files` 화이트리스트로
파일을 골라내지 않고, **검증에 성공한 새 소스로 설치 폴더 전체를 교체**하는 단순한
방식입니다.

1. GitHub `codeload.github.com`에서 저장소 소스를 zip으로 다운로드 (git 바이너리 불필요)
2. 임시 디렉토리에 압축 해제 (Zip Slip 방지 검증 포함)
3. 압축 해제된 소스에 `{repo}.py`(저장소 이름과 같은 메인 모듈 파일)가 있는지 확인
   — 최소한의 신원 확인이며, 소스 코드를 import/exec 하지는 않습니다
4. 확인에 성공한 경우에만 기존 `plugins/metadata/{repo}/`를 삭제하고, 압축 해제된
   소스 **전체**를 그 자리에 복사합니다(README·LICENSE·docs 등 부가 파일 포함).
   확인에 실패하면 기존 설치를 전혀 건드리지 않고 실패로 반환합니다.
5. 가능하면 코어의 hot reload(`services.metadata_factory.MetadataFactory.hot_reload_plugin`)를
   시도해 서버 재시작 없이 즉시 반영 (실패해도 설치 자체는 이미 완료된 상태)

`{repo}.py`가 없는 저장소(BookOasis 플러그인 구조를 따르지 않는 저장소)는 안전을 위해
설치를 거부하며, 이 경우 기존 설치는 그대로 보존됩니다.

**설치/업데이트 성공 시 브라우저를 강제로 새로고침합니다.** 새로 설치된 플러그인의
사이드바 항목·JS/CSS가 실제로 동작하려면 단순히 카드 목록만 다시 그리는 것으로는
부족한 경우가 있습니다(브라우저가 캐시된 리소스를 그대로 쓰는 경우 등). 그래서
성공 토스트를 잠깐 보여준 뒤(1.2초), 브라우저 Cache Storage를 정리하고 현재 URL에
캐시 무효화 쿼리 파라미터를 붙여 `location.replace()`로 페이지 전체를 다시
불러옵니다 — Ctrl+F5(강력 새로고침)와 동등한 효과를 스크립트로 재현한 것입니다.
카드의 `신규설치`/`업데이트` 버튼과 상단 Git 저장소 URL 설치 패널 둘 다 이 방식을
씁니다. (삭제·활성화/비활성화·목록 새로고침은 새 코드를 불러오는 동작이 아니므로
그대로 부분 갱신만 합니다.)

### 6. Git 저장소 URL 설치 패널 — 토픽 검색에 안 잡힌 저장소도 즉시 설치

화면 상단에는 `madnite1/plugin_manager`의 "Git 저장소 URL 설치" 패널과 같은 형태의
입력창이 있습니다. 토픽 검색(§2-1) 결과에 아직 안 잡힌 저장소라도 GitHub 주소만
입력하면 바로 설치할 수 있습니다. 내부적으로는 카드의 `신규설치` 버튼과 동일한
`apply({"action": "install_git", "git_url": ...})`를 호출할 뿐이라, 별도의 백엔드
로직이 추가된 것은 아닙니다. 설치가 끝나면 목록을 새로고침하며, `github.txt`
레지스트리(§2-2)에 자동 기록되어 이후에도 계속 추적됩니다.

### 7. 활성화/비활성화 · 환경설정 · 삭제 — 코어 공통 API 그대로 사용

설치된 카드 하단에는 관리 행이 추가로 표시됩니다.

- **활성화/비활성화 스위치** — 코어 서비스 `services.plugin_service.PluginService
  .toggle_plugin_enabled(...)`를 그대로 호출합니다. plugin_board가 직접 구현하지
  않고 코어에 위임하므로, 다른 화면(예: 환경설정 > 플러그인 설정)에서 본 상태와
  항상 일치합니다.
- **환경설정(⚙) 버튼** — 설치된 플러그인에 `config_schema` 또는 `settings.html`이
  있을 때 표시됩니다. **카드 헤더 우측 상단에 고정 배치**되어 있어(스위치·삭제가
  있는 하단 관리 행과는 별개), 설치 상태와 무관하게 항상 같은 자리에서 찾을 수
  있습니다(`madnite1/plugin_manager`의 카드 레이아웃을 참고해 v2.25.0에서 이 위치로
  옮겼습니다 — 기존에는 하단 관리 행 안에 있어 자기 자신 카드처럼 그 행 자체가
  숨겨지는 카드에서는 설정 버튼도 함께 사라지는 문제가 있었습니다). 클릭하면 모든
  플러그인이 공통으로 쓰는 코어 API를 호출해 설정 화면을 엽니다.
  - 조회: `GET /api/media/metadata/plugins/manage`
  - 저장: `POST /api/media/metadata/plugins/save-config`
  - **설정값 조회는 두 경로를 병합합니다(v2.27.2부터)** — `/manage` API의 `config`
    필드만 믿지 않고, 가이드 문서(§4)가 명시한 저장 위치(`settings` 테이블의
    `PLUGIN_CONFIG_{id}`, JSON 문자열)를 `self.get_db_gateway(db_type)`로 plugin_board가
    직접 한 번 더 조회해서(`apply({"action": "get_config", "plugin_id": ...})`)
    `/manage`의 값과 병합합니다. **겹치는 키는 DB 게이트웨이 조회 결과가 우선**합니다
    — `/manage`가 값을 못 돌려주는 경우에도 실제 DB에 저장된 값이라면 화면에
    반영되도록 하기 위함입니다. 게이트웨이 조회 자체가 실패해도 `/manage`의 값으로
    안전하게 폴백하며, 저장 형식(순수 JSON 문자열 / `{"value": "...json..."}`로
    감싸진 형태) 두 가지를 모두 인식합니다.
  - **`settings.html`이 있으면 그 커스텀 UI를 최우선으로 사용합니다.** 코어가
    렌더링해 내려주는 `settings_ui.html`/`.css`/`.js`를 그대로 모달에 삽입·실행합니다
    (madnite1/plugin_manager의 환경설정 모달과 동일한 방식). `settings.html`이 없으면
    `config_schema` 기반 자동 생성 폼(text / password / number / checkbox / select,
    가이드 §4와 동일)으로 대체합니다.
  - **위에서 병합된 최종 값은 세 가지 경로로 커스텀 UI에 반영됩니다:**
    1. **`name` 속성 기준 범용 자동 채우기** — 커스텀 HTML을 삽입한 직후, 별도 JS 없이도
       `input[name]`/`select[name]`/체크박스를 병합된 설정과 같은 키로 자동 매칭해
       채웁니다. `unified_book`처럼 `settings.js` 자체가 아예 없고 `name` 속성만으로
       값을 저장하도록 만들어진 플러그인은 이 경로로만 채워집니다. 저장된 값이 없는
       필드는 건드리지 않아 플러그인이 HTML에 정해둔 기본값(`selected`/`checked`)이
       그대로 유지됩니다.
    2. `settings.js` 함수 호출 시 네 번째 인자(`config`)
    3. 루트 요소의 `data-plugin-config` DOM 속성(JSON 문자열, `data-plugin-settings-root`
       속성과 함께 설정됨) — 일부 플러그인의 `settings.js`는 함수 인자 대신 이 속성에서
       직접 읽어갑니다.

    1번(범용 채우기)이 가장 먼저 적용되고, 그 다음 2·3번 경로로 플러그인 자체 JS가
    실행되며 필요하면 값을 다시 덮어쓸 수 있습니다. `data-plugin-config`는 HTML
    문자열 조립이 아니라 `setAttribute`로 직접 심으므로 별도 HTML 이스케이프 없이
    JSON 문자열을 그대로 넣습니다 — 미리 이스케이프하면 오히려 다시 읽을 때 깨집니다.
    실제 `unified_book`의 공개 저장소 `settings.html`(JS 없음)로 jsdom 검증까지
    마쳤습니다: 저장된 값이 있으면 하드코딩된 기본 `selected`/`checked`까지 정확히
    덮어쓰고, 저장 이력이 전혀 없으면 플러그인의 기본값을 그대로 보존합니다.
  - 저장은 두 경우 모두 동일하게 폼 안의 `name` 속성이 있는 input/select 값을
    모아 `save-config`로 전송합니다 — `settings.html` 작성 시 입력 요소의 `name`을
    저장하려는 설정 키와 맞추면 됩니다.
  - 모달 너비는 560px, `password` 타입 필드(예: `GITHUB_TOKEN`)에는 값을 점(•)
    대신 평문으로 확인할 수 있는 눈 모양 보기/숨기기 버튼이 붙어 있습니다.
- **삭제(🗑) 버튼** — 확인 대화상자 후 `plugins/metadata/{id}/` 폴더를 삭제합니다.
  경로 검증은 설치 엔진과 동일한 함수(`_validate_plugin_id`, `_safe_join`)를
  재사용합니다. `plugin_board` 자기 자신은 비활성화·삭제 모두 차단됩니다.

이 세 기능 모두 **plugin_manager가 만든 전용 API가 아니라 BookOasis 코어가 모든
플러그인에 공통으로 제공하는 API**를 사용하므로, plugin_manager 설치 여부와
무관하게 동작합니다.

## 설치

최종 폴더 구조는 다음과 같습니다.

```
plugins/metadata/plugin_board/
├── __init__.py
├── plugin_board.py
├── README.md
├── VERSION
├── index.html
├── style.css
└── script.js
```

(`.cache.json`은 배포에 포함할 파일이 아니라, 플러그인이 실행되면서 이 폴더에 자동으로
생기는 캐시 파일입니다. 지워도 안전합니다.)

1. 위 폴더를 서버의 `plugins/metadata/plugin_board/`에 그대로 배치합니다.
2. BookOasis 서버를 재시작합니다.
3. 환경설정 > 플러그인 설정에서 `플러그인게시판`을 활성화합니다.
4. (선택) `GitHub Personal Access Token`을 입력하면 API 호출 한도가 늘어납니다.
5. 좌측 사이드바의 `플러그인게시판` 카테고리에서 카드별로 설치·업데이트·활성화·설정·삭제를
   사용합니다.

## ZIP 파일 업로드 설치 (v2.35.0) — zip 외 tar 계열·7z 지원 (v2.36.0)

`madnite1/plugin_manager`의 실제 `_install_from_zip` 구현을 그대로 참고해
재구현했습니다. Git 저장소 URL 설치와 나란히, 화면 상단에 "압축 파일 업로드 설치"
패널이 표시됩니다(관리자만 — §관리자 전용 접근 제어 참고).

**지원 형식**: `zip`, `tar`/`tar.gz`(`tgz`)/`tar.bz2`(`tbz2`)/`tar.xz`(`txz`),
`7z`. 파일명 확장자로 형식을 자동 판별합니다.

- zip/tar 계열은 파이썬 표준 라이브러리(`zipfile`/`tarfile`)만으로 동작하며
  별도 설치가 필요 없습니다.
- **7z는 파이썬 표준 라이브러리에 압축 해제 기능이 없어 서드파티 `py7zr`이
  필요**합니다. 이 라이브러리는 별도로 설치하지 않으며, 서버에 없으면
  "이 서버에는 7z 압축 해제 라이브러리(py7zr)가 설치되어 있지 않아..."라는
  명확한 안내로 그 요청만 실패시킵니다 — import 실패가 카드 조회 등 다른
  기능에는 전혀 영향을 주지 않습니다. 서버 관리자가 `pip install py7zr`로
  직접 설치하면 별도 코드 수정 없이 자동으로 7z도 지원됩니다.
- tar 계열도 zip과 동일한 안전장치(경로 이탈 차단·항목 개수/총 용량 상한)를
  거치며, tar 고유의 위험인 **심볼릭/하드 링크 멤버는 아예 거부**합니다
  (실제로 경로 이탈 시도와 심볼릭 링크 포함 tar 둘 다 정상적으로 거부되는
  것을 재현 테스트로 확인).

**동작 방식**

1. 업로드된 압축 파일을 base64로 받아, 파일명 확장자로 형식을 판별한 뒤
   임시 폴더에 안전하게 압축 해제합니다(형식별 안전장치는 위 참고).
2. 압축 해제된 폴더 안에서(중첩 폴더여도) 실제 플러그인 루트를 지능 탐색하고,
   `VERSION`/코드 내 `id=` 속성/폴더명/업로드 파일명 순으로 플러그인 ID를
   결정합니다.
3. **정적 소스 검증**(코드를 실행하지 않고 AST/파일 스캔만 수행) — VERSION 형식,
   `BaseMetadataProvider` 상속 여부, 클래스 `id`와 감지된 ID 일치 여부, 필수
   필드(`name`/`is_searchable`/`config_schema`), 필수 메서드(`search`/`apply`),
   금지 패턴(`eval`/`exec`/`subprocess`/`os.system`/`shell=True`), 심볼릭 링크
   금지, `category_tab` 선언 시 UI 번들(`index.html`/`script.js`/`style.css`)
   필수 여부까지 확인합니다. **검증에 실패하면 기존 설치는 전혀 건드리지 않고
   설치를 중단**합니다.
4. 검증을 통과해야만 기존 폴더를 교체하고, 활성화 + 핫 리로드 후 **실제로
   코어가 이 플러그인을 로드했는지 2차로 재확인**합니다 — 로드가 안 됐으면
   설치 폴더 자체를 삭제해 롤백합니다(클래스 `id`와 폴더명이 다른 경우 등).
5. **`update_manifest.raw_base_url`이 GitHub 루트(또는 Gitea) 저장소를 정확히
   가리키면**, 설치 방식(zip/tar/7z)과 무관하게 §2-2의 `github.txt` 레지스트리에
   등록해 이후에도 계속 업데이트를 추적합니다(monorepo 서브디렉토리는 릴리즈
   기준이 안 맞아 제외). 이 레지스트리 등록은 **2차 로드 검증을 통과한 뒤에만**
   기록합니다 — 검증 실패로 롤백된 설치가 레지스트리에 존재하지 않는 플러그인을
   가리키는 상태로 남지 않도록 순서를 맞췄습니다. `update_manifest`가 없으면
   설치는 되지만 로컬 플러그인으로 남아 업데이트 추적 대상이 아닙니다.

**plugin_manager와의 차이점**: plugin_manager는 소스 메타를 자체 sqlite
(`plugin_sources.db`)에 저장하지만, plugin_board는 이미 있는 §2-2의
`github.txt` 파일 기반 레지스트리를 그대로 재사용합니다 — 설치 방식(Git URL/
zip)과 무관하게 동일한 파일에 기록되므로 관리가 더 단순합니다.

**검증**: 깊이 중첩된 폴더 구조의 zip도 정확히 플러그인 루트를 찾아 설치되는
것, 금지 패턴(`os.system`) 포함 zip이 거부되는 것, 시스템 예약어(`plugin_manager`)
덮어쓰기가 거부되는 것, `update_manifest` 없는 zip은 설치는 되지만 레지스트리에
안 남는 것, 그리고 2차 로드 검증 실패 시 설치 폴더와 레지스트리 양쪽 모두
롤백되는 것까지 전부 재현 테스트로 확인했습니다.

## 토픽 검색 시각 표시 (v2.43.0)

집계(등록 플러그인/설치됨/토픽 발견 등) 바로 아래에 **"🔍 토픽 검색: N분 전
(HH:MM 기준, 최대 1시간마다 자동 갱신)"** 문구가 추가됩니다. GitHub Topics
검색(§2-1)이 카드 목록의 유일한 수집 경로가 된 이후, 지금 보이는 카드 목록이
실제로 언제 검색된 결과인지(캐시가 얼마나 오래됐는지) 한눈에 알 수 있도록
하기 위함입니다.

- 백엔드는 `_TOPIC_CACHE`에 이미 기록해두던 타임스탬프를 그대로 읽어와
  `get_dashboard_data()` 응답의 `topic_search_at`(초 단위 epoch)로 내려줍니다.
  검색 캐시가 살아있어 이번 요청에서 재검색을 안 했어도, 이전 검색 시각이
  그대로 남아있으므로 항상 정확합니다.
- 프론트엔드는 이 값을 "방금 전" / "N분 전" / "N시간 전" / "N일 전"으로
  환산해 절대 시각(HH:MM)과 함께 보여줍니다. 검색 이력이 전혀 없는 최초
  상태(`topic_search_at`이 없음)에서는 문구 자체를 표시하지 않습니다.
- `목록 새로고침` 버튼을 누르면 토픽 캐시가 강제로 비워지고 곧바로 재검색되므로,
  이 문구도 "방금 전"으로 즉시 갱신됩니다.

## Gitea 주소의 http/https 스킴을 그대로 존중 (v2.42.0)

**증상**: `http://아이디:비밀번호@호스트/owner/repo` 형식으로 **http** 주소를
입력했는데도 카드에 "Gitea API 호출 오류 (HTTP 523)"이 떴습니다. 523은
Cloudflare 등 프록시가 "origin(원본 서버)에 도달할 수 없다"는 뜻으로 반환하는
코드로, 실제 Gitea 서버는 http로만 서비스되는데 저희 코드가 **입력받은 스킴과
무관하게 항상 https로 강제 접속**하고 있었던 게 원인이었습니다.

**고친 내용**: `_url_scheme(url)` 헬퍼를 추가해 사용자가 준 URL의 스킴(http/https)
을 그대로 존중하도록 Gitea 관련 함수 전체(`_gitea_get_json`/`_gitea_get_text`/
`_gitea_download_zip`/`_gitea_fetch_description_info`/`_gitea_fetch_version`/
`_gitea_fetch_version_info`/`_fetch_gitea_repo_entry`/`_install_or_update_gitea`)
에 `scheme` 매개변수를 관통시켰습니다. 카드 조회, zip 다운로드를 통한 설치,
카드에 표시되는 링크 URL까지 전부 원래 입력한 스킴을 그대로 씁니다(기본값은
기존과 동일하게 `https`이므로 스킴을 명시하지 않은 기존 설정은 영향이 없습니다).

실제로 `http://` 주소로 조회·설치 전체 흐름을 스텁으로 재현해, 매 단계에서
정확히 `http`로 요청이 나가는 것과 카드에 표시되는 URL도 `http://`를 유지하는
것까지 확인했습니다. `https://` 주소는 기존과 동일하게 계속 정상 동작합니다(회귀
테스트 통과).

## 401(인증 실패)과 403(호출 제한)을 구분한 오류 메시지 (v2.41.0)

**증상**: GitHub API 호출이 401(Bad credentials)로 실패해도 화면에는
"GitHub API 호출 제한 또는 오류(401)"라고만 떠서, 실제로는 **설정한
`GITHUB_TOKEN`이 잘못됐거나 만료/폐기된 상황**인데도 마치 rate limit(요청
횟수 초과) 문제처럼 보였습니다. 401과 403은 원인이 완전히 다른데도 하나의
모호한 문구로 뭉뚱그려져 있었던 것입니다.

**고친 내용**: `_github_api_error_message()` 공통 헬퍼를 만들어 원인별로
명확히 구분합니다.

| 상황 | 메시지 |
| --- | --- |
| 401 + 토큰 설정됨 | "GitHub 인증 실패(401) — 설정한 GITHUB_TOKEN이 잘못됐거나 만료/폐기됐을 수 있습니다. GitHub에서 토큰을 다시 확인하거나 새로 발급해 설정에 저장해주세요." |
| 401 + 토큰 없음 | "GitHub 인증 실패(401) — 원인을 알 수 없는 인증 오류입니다. 잠시 후 다시 시도해주세요." |
| 403 + 토큰 설정됨 | "GitHub API 호출 제한(403) — 인증된 토큰 기준 한도(시간당 5,000회)를 초과했을 수 있습니다." |
| 403 + 토큰 없음 | "GitHub API 호출 제한(403) — 무인증 한도(시간당 60회)를 초과했습니다. GITHUB_TOKEN 설정을 권장합니다." |
| 그 외 | "GitHub API 오류(코드)" |

카드 설명(`_fetch_description_info`)뿐 아니라 설치/업데이트 엔진
(`_install_or_update`)의 zip 다운로드 실패 메시지에도 동일하게 적용했습니다.
실제로 401을 흉내낸 상황에서 카드 설명과 설치 실패 메시지 둘 다 "토큰을
다시 확인해달라"는 문구가 정확히 뜨는 것까지 확인했습니다.

## 다운로드 횟수 대신 별(star) 개수 표시 (v2.34.0)

GitHub는 자기가 소유하지 않은 저장소의 클론/다운로드 통계(Traffic API)를 공개로
제공하지 않습니다(저장소 소유자·협업자만 조회 가능). Release 자산의
`download_count`는 있지만, 이 플러그인의 설치 방식(브랜치 zip 직접 다운로드)은
Release를 쓰지 않아 해당되지 않습니다. 그래서 "다운로드 횟수" 대신, GitHub/Gitea
API 응답에 이미 포함돼 있어 추가 호출 없이 쓸 수 있는 **별(star) 개수**를 참고용
인기도 지표로 카드 하단에 표시합니다.

- 1,000개 이상은 `1.2k`처럼 축약 표시합니다.
- 카드에 마우스를 올리면(hover) "다운로드 횟수가 아닌 참고용 인기도 지표"라는
  안내가 툴팁으로 뜹니다 — 오해 소지를 줄이기 위함입니다.
- GitHub 큐레이션 카드·토픽 발견 카드·Gitea 카드 전부 지원합니다. GitHub API
  호출이 실패(rate limit 등)한 경우에는 별 개수도 함께 비어 보일 수 있습니다
  (설명·버전과 같은 신뢰도).

## 관리자 전용 접근 제어 (v2.33.0)

설치·업데이트·삭제·활성화/비활성화·설정 조회는 **관리자(role == 'admin')만** 할 수
있습니다. `api/auth.py`의 `admin_required` 데코레이터와 동일한 기준(Flask
`session.get('role') == 'admin'`)으로 판단합니다.

- **화면**: 관리자가 아니면 설정(⚙) 버튼, 활성화 스위치·삭제 버튼(관리 행), Git
  저장소 URL 설치 패널이 전부 보이지 않습니다. 설치/업데이트가 필요한 카드에는
  버튼 대신 "미설치 (관리자 전용)" / "업데이트 필요 (관리자 전용)" 같은 정보성
  문구만 표시됩니다.
- **API도 동일하게 막습니다** — 화면에서 버튼을 숨기는 것만으로는 개발자도구로
  API를 직접 호출하는 우회를 막을 수 없으므로, `install_git`/`update`/`toggle`/
  `delete`/`get_config` 액션은 백엔드(`_dispatch_apply`)에서도 관리자 여부를
  다시 확인합니다. 목록 새로고침(`refresh_list`)은 카드 목록만 다시 불러오는
  무해한 동작이라 모든 사용자에게 허용됩니다.
- **세션에 `role` 정보 자체가 없는 경우**(구버전 코어 등 role 기반 세션이 없는
  환경)에는 안전하게 관리자로 간주해 기존처럼 모든 기능을 그대로 보여줍니다 —
  이 기능 도입 이전과 동작이 달라지지 않도록 하기 위함입니다.
- 실제로 role 없음/`user`/`admin` 세 가지 세션 상태를 각각 흉내내어, 카드
  조회·설치·활성화 토글·목록 새로고침이 의도대로 허용/거부되는 것까지 확인했습니다.



`GITHUB_TOKEN`을 설정하지 않은 서버(무인증 시간당 60회 한도)에서 실제로 한도를
자주 초과한다는 피드백을 반영해 두 가지를 고쳤습니다.

1. **설치/업데이트 버튼의 중복 API 호출 제거** — `신규설치`/`업데이트`를 누르면
   내부적으로 대상 저장소의 기본 브랜치(`default_branch`)를 알아야 하는데, 지금까지는
   이걸 매번 새로 `api.github.com`에 조회했습니다. 사실 이 값은 카드 목록을 불러올 때
   (설명·토픽 조회, 24시간 캐시) 이미 받아둔 값과 완전히 같습니다. 이제 그 캐시를
   그대로 재사용해서, 카드 목록을 한 번이라도 불러온 뒤라면 설치 버튼을 몇 번을
   눌러도 추가 코어 API 호출이 발생하지 않습니다.
2. **캐시를 디스크에도 저장(재시작 후에도 유지)** — 지금까지는 캐시가 메모리에만
   있어서 서버가 재시작될 때마다(배포, 컨테이너 재시작 등) 전부 사라지고 다음
   요청이 처음부터 다시 GitHub를 두드렸습니다. 이제 이 폴더의 `.cache.json`에도
   함께 저장해서, 서버가 재시작돼도 TTL이 남아있는 캐시는 그대로 이어받아 씁니다.
   `.cache.json`은 순수 성능 캐시라 지워도 안전하며(다음 요청 때 다시 채워짐), 실제로
   "재시작"을 흉내낸 테스트에서 재시작 직후 조회가 `api.github.com` 코어 API를 한 번도
   부르지 않는 것까지 확인했습니다.

그래도 여러 BookOasis 서버가 같은 공인 IP를 공유하거나(사내망, 같은 호스팅사 등)
플러그인을 자주 설치/삭제하며 캐시를 계속 비우는 경우엔 무인증 한도(시간당 60회)를
넘길 수 있습니다. 이럴 땐 `GITHUB_TOKEN`에 **아무 권한도 주지 않은(Fine-grained PAT,
Repository access: None)** 개인 액세스 토큰만 넣어도 시간당 5,000회로 늘어납니다 —
공개 저장소 정보만 읽으므로 권한을 하나도 부여하지 않아도 되고, 발급도 GitHub
설정에서 1분이면 끝납니다.

**화면에서도 바로 안내를 볼 수 있습니다.** 헤더 바로 아래 "GitHub API 호출 제한이
자주 걸리시나요? — 토큰 발급 안내"를 펼치면, 토큰 발급 페이지로 바로 이동하는
버튼과 함께 발급 단계, 그리고 발급받은 토큰을 붙여넣을 위치(환경설정 → 플러그인
설정 → 플러그인게시판 카드의 `GitHub Personal Access Token` 입력란)까지 이 문서를
따로 안 봐도 화면 안에서 전부 확인할 수 있습니다.

| `GITHUB_TOKEN` | password | 선택 | GitHub Personal Access Token. 설명/토픽 조회(`api.github.com`)의 무인증 한도(60/시간)를 늘리는 용도. 목록 조회(`raw.githubusercontent.com`)와 설치용 소스 다운로드(`codeload.github.com`)는 공개 저장소라면 토큰 없이도 동작. 자격증명이 담기지 않은 URL의 폴백 토큰으로도 쓰입니다. **저장소별로 다른 자격증명이 필요하면(비공개 저장소 등) URL에 직접 담는 방식(§2-3, §2-4)을 쓰세요** |
| `EXTRA_DISCOVERY_TOPICS` | text | 선택 | GitHub Topics 발견(§2-1) 대상에 추가할 토픽(콤마 구분). 기본 `bookoasis-plugin`에 더해집니다. 흔한 단어는 무관한 저장소를 대량으로 끌어올 수 있어 구체적인 이름만 권장 |
| `AUTO_UPDATE_ENABLED` | checkbox | 선택 | **기본값 꺼짐.** 켜면 활성화(사용 중)된 플러그인에 새 버전이 있을 때 화면을 열 때마다 자동으로 업데이트를 시도합니다(§9 참고) |

### 사용 중인 플러그인 자동 업데이트 (선택, 기본 꺼짐)

설정의 `사용 중인 플러그인 자동 업데이트` 체크박스를 켜면, 카드 목록을 불러올 때마다
다음 조건을 **모두** 만족하는 플러그인을 자동으로 업데이트합니다.

- 설치되어 있음(`installed`)
- 활성화(사용 중) 상태(`enabled`) — 비활성화(중지됨)된 플러그인은 건드리지 않습니다
- GitHub 최신 버전이 설치된 버전보다 높음(`has_update`)
- GitHub 저장소 주소를 알고 있음(`url`) — 로컬 전용(local_only) 카드처럼 출처를 모르는
  플러그인은 애초에 `has_update`가 항상 false라 대상이 되지 않습니다

`plugin_board` 자기 자신도 이 조건을 만족하면 대상에 포함됩니다(카드의 `업데이트`
버튼으로 직접 누르는 것과 동일한 §5의 전체 재다운로드 방식을 그대로 사용합니다).
대상이 여러 개면 서버 자원을 한 번에 많이 쓰지 않도록 **하나씩 순차적으로** 처리하고,
완료되면 어떤 플러그인이 갱신됐는지 토스트로 요약해 보여줍니다. 카드의 `업데이트`
버튼을 직접 눌렀을 때와 달리, 자동 업데이트는 페이지 전체를 강제로 새로고침하지
않고 카드 정보만 조용히 다시 불러옵니다(사용자가 다른 작업을 하고 있을 수 있는
백그라운드성 동작이라 예고 없이 화면이 새로고침되면 방해가 될 수 있기 때문입니다).

같은 세션에서 너무 자주 반복 실행되지 않도록 5분의 쿨다운을 둡니다. 여러 개를
동시에 업데이트하는 게 아니라 이미 최신인 플러그인은 다음 실행 때 자동으로
제외되므로(`has_update`가 false가 됨), 반복 실행 자체가 무한 루프로 이어지지는
않습니다.

**인증이 필요한 저장소(Gitea 비공개 저장소 등)도 자동 업데이트 대상이 됩니다.**
자동 업데이트 요청에는 화면 표시용 URL을 보내지 않고 `plugin_id`만 보내서, 백엔드가
`github.txt`에 저장해둔 자격증명 포함 URL(§2-4)을 직접 찾아 씁니다 — 설치할 때 쓴
아이디/비밀번호가 자동 업데이트 때도 그대로 재사용됩니다(v2.32.2에서 이 부분의
버그를 수정했습니다).

## 새 저장소를 카드에 나타나게 하려면

`plugin_board.py`를 건드릴 필요 없이, 그 저장소의 GitHub 설정에서 Topics에
`bookoasis-plugin`만 추가하면 됩니다(§2-1). 다음 캐시 만료(최대 1시간) 또는
`목록 새로고침` 버튼을 누르면 자동으로 카드가 나타납니다. `plugin_board.py`/
`index.html`/`script.js`는 수정할 필요가 없습니다.

토픽을 달기 전에 먼저 확인하고 싶다면, 화면 상단 "Git 저장소 URL 설치" 패널에
GitHub 주소만 붙여넣어도 즉시 설치할 수 있습니다(§6) — 설치에 성공하면
`github.txt` 레지스트리(§2-2)에 기록되어 토픽 여부와 무관하게 계속 추적됩니다.

**전제 조건**: 대상 저장소의 메인 모듈 파일명이 저장소 이름과 같아야 합니다
(예: `pixiv_ranking` 저장소 → `pixiv_ranking.py`). 이 가이드가 예시로 제시하는 폴더형
플러그인 구조(`my_plugin/my_plugin.py`)를 따르는 저장소라면 대부분 해당됩니다.
저장소 이름에 하이픈(`-`)이 있는 경우(예: `bookoasis-tk`)는 파이썬 파일명에 하이픈을
쓸 수 없어 언더스코어로 지은 경우(`bookoasis_tk.py`)도 자동으로 함께 확인하므로
별도 조치가 필요 없습니다.

### 분류(검색형 메타데이터 / 카테고리 탭 UI) 지정 — 선택 사항

GitHub API·README만으로는 저장소가 "검색형 메타데이터"인지 "카테고리 탭 UI"인지 자동으로
구분할 수 없습니다. 상단 필터 버튼에서 구분해서 보고 싶다면 `plugin_board.py`의
`TYPE_OVERRIDES`에 `"owner/repo": "search"` 또는 `"tab"`을 추가하세요. 지정하지 않으면
화면에 "기타"로 표시되며, 필터 버튼도 실제 데이터에 존재하는 분류만 자동으로 생성됩니다.
(이미 설치된 저장소는 소스에서 자동으로 재추정되므로 `TYPE_OVERRIDES`보다 우선합니다.)

**"미설치" 필터(v2.37.0)**는 이 분류(검색형/카테고리 탭/기타)와는 별개 축이라
항상 맨 뒤에 고정으로 추가됩니다 — `type`과 무관하게 `installed`가 false인
카드만 모아 보여주며, 버튼 라벨에 개수(`미설치 (N)`)도 함께 표시됩니다.

**"제작자별" 필터(v2.38.0)**도 마찬가지로 분류·설치 여부와는 별개 축이라,
필터 버튼 줄 오른쪽에 별도 드롭다운으로 추가됩니다. 각 카드의 `owner`(저장소
소유자 — GitHub 사용자명/조직명 또는 Gitea 사용자명)를 기준으로 자동 집계해
`제작자명 (N)` 형태의 목록을 만들며, 위의 분류/설치여부 필터와 **AND로 함께
적용**됩니다(예: "카테고리 탭 UI" + "yume-script" 동시 선택 시 두 조건을 모두
만족하는 카드만 표시). 선택된 제작자의 마지막 플러그인이 삭제되는 등 목록에서
사라지면 자동으로 "전체 제작자"로 되돌아갑니다.

```python
TYPE_OVERRIDES = {
    "javara999/naverkakaoridi": "search",
    "owner/new_plugin": "tab",   # 추가 (생략 가능)
}
```

## 자동 업데이트 (plugin_board 자기 자신)

`update_manifest`에 GitHub raw 기반 업데이트 계약이 선언되어 있습니다.

```python
update_manifest = {
    "enabled": True,
    "provider": "github-raw",
    "raw_base_url": "https://raw.githubusercontent.com/yume-script/plugin_board/refs/heads/main",
    "files": [
        "plugin_board.py", "__init__.py", "VERSION",
        "index.html", "style.css", "script.js", "README.md",
    ],
    "version_file": "VERSION",
    "version_key": "plugin version",
    "show_sample_update_button": True,
}
```

`raw_base_url`은 `yume-script/plugin_board` 저장소 루트를 직접 가리키며(그 저장소의
파일이 `plugins/metadata/plugin_board/` 하위가 아니라 저장소 루트에 바로 있는 구조),
`files`에는 이 폴더의 7개 파일을 전부 등록해 전체가 업데이트 대상에 포함됩니다.
GitHub의 `VERSION`이 로컬보다 높을 때만 환경설정 화면의 샘플 업데이트 버튼으로
갱신됩니다. (이 계약은 plugin_board 자신을 업데이트하는 용도이며, §5의 전체
재다운로드 설치 엔진과는 별개의 코어 표준 메커니즘입니다.)

## 보안 관련 설계 메모

- **경로 이탈 방지**: 설치 대상 경로(`_safe_join`)와 zip 압축 해제(`_extract_zip_safe`)
  모두 결과 경로가 `plugins/metadata/` 하위인지 매번 검증합니다.
- **플러그인 ID 검증**: 저장소 이름은 영문·숫자·`_`·`-`만 허용합니다.
- **최소 신원 확인 후 교체**: `{repo}.py`(메인 모듈) 존재를 먼저 확인하고, 그 확인을
  통과한 뒤에야 기존 설치 폴더를 삭제하고 새 소스로 교체합니다. 확인에 실패하면
  기존 설치를 전혀 건드리지 않습니다. 다운로드한 소스는 이 확인 과정에서 import/exec
  되지 않고 파일 존재 여부만 확인합니다 — 단, 설치 자체를 진행하면 그 플러그인의 코드는
  BookOasis가 정상적으로 로드해 실행합니다(플러그인 설치는 본질적으로 해당 저장소의
  코드 실행을 신뢰하는 행위이므로, 신뢰할 수 있는 저장소만 설치해야 합니다).
- **비-플러그인 폴더 제외**: `plugins/metadata/` 스캔 시 `__pycache__`, `-`, 숨김 폴더 등은
  제외하고, `{폴더명}.py` 또는 `VERSION` 파일이 실제로 있는 폴더만 플러그인으로 인정합니다.
- **목록 출처 신뢰**: 카드 목록은 GitHub Topics 검색(`bookoasis-plugin`)과
  `github.txt` 레지스트리로만 구성됩니다. 검색 대상 토픽을 코드 배포 없이
  늘리려면 설정의 `EXTRA_DISCOVERY_TOPICS`를 쓰세요(§2-1).
- **커스텀 설정 UI 실행**: `settings.html`/`settings.js`는 신뢰된 관리자 화면(환경설정)에서만
  삽입·실행되며, plugin_manager와 동일하게 `new Function(...)`으로 실행됩니다. 이미 설치를
  허용한 플러그인의 코드이므로 별도로 샌드박싱하지 않습니다.

## 제한 사항

- 검색/메타데이터 적용은 지원하지 않는 안내·설치·관리용 플러그인입니다(`is_searchable = False`).
- GitHub API 무인증 한도(60회/시간)를 서버 전체가 공유합니다. `GITHUB_TOKEN` 설정을 권장합니다.
- 기능 목록(`features`)은 GitHub API로 자동 추출하지 않으므로 기본적으로 비어 있습니다.
- Git URL 설치 패널·`신규설치`/`업데이트` 버튼 모두 저장소에 `{repo}.py` 메인 모듈이
  있어야 동작합니다(가이드의 폴더형 플러그인 구조 관례).
- 설치/업데이트는 대상 폴더를 **완전히 교체**합니다. 설치 폴더 안에 수동으로 넣어둔
  파일이 있다면 다음 업데이트 때 사라집니다.
